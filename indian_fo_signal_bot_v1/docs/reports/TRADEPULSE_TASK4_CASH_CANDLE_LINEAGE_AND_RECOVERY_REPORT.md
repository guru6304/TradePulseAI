## Confirmed existing flow and defect

Adapters normalize provider responses. `MultiBrokerScanner.fetch_candles` binds identity and enforces the shared live batch contract; `IntradayBotEngine._fetch_scan_candles` checks canonical identity and rechecks freshness. The scanner obtains index/equity maps, computes breadth, calls existing strategy evaluators, validates/ranks/sizes signals, and persists them through `SQLitePersistenceStore.save_signal`. Signal rows reference `scan_run_id`, not immutable input batches. Scan rows, OI snapshots/baselines and mitigated-zone writes use separate SQLite connections/transactions. The paper coordinator runs afterward with its existing atomic event keys.

The current scanner keeps accepted candle maps only in memory. Signal writes can succeed before zone/scan writes fail. Required persistence already blocks notification dispatch on detected errors, but the overall scan is not an atomic database result. Recovery needs the completed input bars, their validation/reference clock, instrument/provider binding, original zone state, strategy/risk/calendar configuration, code fingerprint, scan result and stable signal/input links. Paper recovery also needs the original scan ID and observations; committed paper effects must continue to use existing idempotency rules.

## Design recorded before coding

Use additive SQLite tables and the existing store. Keep accepted completed cash candles separate from incomplete display tails and auxiliary index/option inputs. A stable content digest detects local content changes only; it does not authenticate a publisher. Natural candle keys reject conflicting corrections rather than silently overwriting old accepted bars.

Transaction A will persist validated cash batches, unique candle facts, their membership and a pending scan/input linkage together. Nothing is accepted before the existing identity, OHLCV, timestamp/grid/session, freshness and provenance checks pass. Incomplete tails are excluded from evaluator input and never inserted as accepted candles. Repeated ingestion is idempotent; a conflicting natural candle key fails closed.

Transaction B will serialize pending work and commit signals, zone state, scan metadata and durable result together, using the existing writer implementations on one borrowed connection. Implicit inner context-manager commits must not escape the outer transaction. Acquisition happens before the write transaction. Notifications run only after successful commit; recovery suppresses them. This is at-most-once recovery behavior, not a durable Telegram outbox or a guarantee of message delivery.

Explicit offline recovery will read and validate retained inputs at their original acceptance reference, require matching nonsecret configuration/code fingerprints and run the existing evaluators without transport. Recovered output must identify its original observation scope and cannot establish current freshness, live acceptance or historical source qualification. The existing paper coordinator remains a separate idempotent handoff after the committed scan; retries recover effects instead of inventing fills.

## Accepted input and schema contract

The ingestion version is `cash-lineage-v1`. Accepted cash records require explicit `LIVE`, `is_simulated=false`, `Asia/Kolkata`, interval 5 and boolean completion metadata. They must pass the existing identity binding and `assess_live_candle_batch` at the recorded original reference: finite coherent OHLCV, order, duplicates, gaps, time grid, session/calendar, future skew and freshness. The identity is EQ with matching configured provider/instrument and supported source metadata. Missing provenance is rejected, never inferred. Incomplete tails are excluded after whole-response validation; a batch with no acceptable completed input is rejected. Synthetic test fixtures exercise the strict branch, but are not production history or provider acceptance.

| Table | Durable content and reconciliation role |
| --- | --- |
| `cash_candle_facts` | Unique natural candle key (provider, validated identifier, exchange, segment, interval, timestamp); canonical completed OHLCV/quantity/provenance payload and content digest. |
| `cash_candle_batches` | Immutable content ID, count, metadata JSON and metadata digest. Header retains provider, exchange/segment/symbol/token identity, source/revision/validity/response binding and interval; bars retain normalized timestamp/timezone/completion and supported quantity. |
| `cash_candle_batch_members` | Exact ordinal-to-candle membership; primary/unique keys and foreign keys prevent duplicate membership. |
| `cash_candle_scans` | Unique run/work IDs, immutable input snapshot/digest, `PENDING` or `COMMITTED`, immutable result/digest. Snapshot retains nonsecret parameters/calendar/universe, Python/SQLite versions, production-code fingerprint, original reference, auxiliary inputs, acquisition errors and frozen zones. |
| `cash_candle_scan_inputs` | Exact scan-to-accepted-cash-batch links, including zero-signal scans. |
| `cash_candle_signal_inputs` | Scan + existing signal dedup key + exact accepted cash batch; reconciled against original result and actual signal/scan rows. |

Batch metadata records the local reference/retrieval observation clock, validation report/reason and excluded forming-tail count. `source_observation_at=null` is explicit: current normalized candle inputs do not supply an independent publisher observation time. Derived bar end and local acquisition time are not substituted for it. `source_authenticity=NOT_ESTABLISHED` remains explicit; local hashes do not authenticate any publisher. Original retrieval metadata stays attached to the first immutable accepted batch; later reingestion does not overwrite it or create a new retrieval history.

Canonical JSON rejects nonfinite values and snapshots above 32 MiB; a cash batch is bounded to 25,000 rows. These are local safety bounds, not evidence of historical-scale acceptance. No credentials, configuration paths, destination IDs or account IDs are in the runtime profile. Only execution/calendar/risk fields, instrument metadata and runtime versions are retained.

Same content is reused. Different content for an already accepted natural candle key raises `LINEAGE_CANDLE_CORRECTION_CONFLICT`; there is no silent update or automatic provider-correction policy. A future amendment/import workflow would need separate auditable design. Different configuration/code/auxiliary input produces distinct work identity, while retrieval clock and zone snapshot do not create duplicate work for the same accepted inputs. Different pending work for one provider is rejected with `LINEAGE_PRIOR_SCAN_REQUIRES_RECOVERY`; original work remains discoverable and must be resumed first.

## Transaction and recovery behavior

1. Acquisition and existing identity/candle gates run before any accepted-input write. Required storage absent at startup stops a live-path scan before acquisition. Simulated scans and explicit persistence-disabled behavior retain their existing contracts.
2. Transaction A uses existing SQLite `BEGIN IMMEDIATE`: candle facts, immutable batch/membership, pending work, frozen committed zone state and scan/input links commit together. Any failure before commit rolls all these back. Input commit does not claim a successful scan. The existing WAL/foreign-key/store lock conventions remain in use.
3. Transaction B takes the SQLite write lock, reloads and reconciles work, and uses the retained completed cash bars in existing breadth/evaluation/ranking/sizing code. Signals, scan-time OI writes, consumed zones, scan row, cash signal links and immutable result commit together. Legacy writer contexts borrow the owner connection; exceptions and swallowed inner SQL failures prevent commit. An aborted result retains transaction A as `PENDING`, with no result/signal/zone rows from that attempt.
4. Notifications occur only after successful result commit and a current-freshness recheck. Recovery and repeated committed work never dispatch. The stored immutable result has truthful `delivery_not_recorded` placeholders; the caller may receive a later dry-run dispatch result. Commit is not proof of delivery. A crash can lose a notification; a durable outbox is still B10.
5. The existing paper coordinator runs after result commit in its own transactions. Its original account/event/decision keys remain authoritative. Replaying a committed scan can reconcile an interrupted paper handoff without repeating capital, fees or positions. Paper acceptance remains cash-only and simulated.

Use `store.pending_cash_scans(limit=100)` for bounded discovery (permitted range 1..200), `store.load_cash_scan(run_id)` for reconstructed input/result inspection, and `engine.resume_cash_scan(run_id, paper_portfolio=optional_same_account)` for explicit offline recovery. The engine/store must use the same database and unchanged execution profile/production code/runtime; Telegram dry-run must be true and scheduler false. Recovery uses the recorded acceptance reference and revalidates stored inputs there; it calls no candle/chain acquisition and suppresses notification transport. It does not establish current market freshness. Changed code/configuration fails closed, requiring the matching original environment or a separately designed migration rather than silently rerunning a different strategy.

Pending recovery evaluates the original accepted input and frozen zones. Committed replay returns `idempotent_replay=true`, the original immutable result separately, and zero newly generated/persisted signals. Scan status is the original status; replay is not a second zero-signal scan. Every read rechecks payload/membership/snapshot/result digests, natural identities and input links; committed reads additionally reconcile the actual scan totals, signal rows and signal links. Detected corruption requires investigation; it is not automatically repaired or reclassified as accepted.

Boundaries are explicitly scoped to accepted cash input and its scanner result. Auxiliary index candles and option chains are retained for breadth/context but are not accepted cash records. Existing Angel master state and pre-acquisition option/OI baseline behavior are not a new atomic F&O ingestion system. General historical/option reproduction across external master or OI state changes is not claimed. No authoritative calendar ingestion, source authenticator, historical provenance qualification, durable outbox, automatic pending cancellation or schema/data amendment workflow is added.
