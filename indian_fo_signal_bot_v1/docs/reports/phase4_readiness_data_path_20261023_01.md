## Findings for later permitted remediation

**DP-01 — real scanner-consumer evidence is still missing (acceptance gap, high).** `angel_feed_control.py:193` attaches the feed only to the isolated adapter, collects its status and detaches/stops it before evaluating the diagnostic sub-gates. At `:217`, even successful completed candles yield `LIVE_SCANNER_CONSUMER_ACCEPTANCE_NOT_ESTABLISHED`. The command does not instantiate `IntradayBotEngine` or call `run_single_scan`. `test_phase3_angel_integration.py:243` intentionally asserts this separation. Therefore the existing long diagnostic, even if it later observes valid candles, cannot alone establish the actual scanner-consumer gate. A separately permitted real consumer-path receipt must link the genuine feed's accepted events/candles, the scanner run, its persisted input/result identifiers, safe empty-or-candidate output and clean shutdown. No replacement receipt was synthesized here.

**DP-02 — default scanner universe exceeds the feed scope (static integration mismatch, high).** `config.py:168` defaults to two F&O indices and `:188` a multi-equity watchlist. `scanner_engine.py:613` acquires index inputs before cash inputs and subsequently acquires every configured equity. The current Angel stream accepts exactly one verified NSE cash identity and rejects index/other-token requests. Unmodified default scanning against that attached feed will fail closed before a scoped cash scan can complete. Future acceptance must explicitly reconcile the runtime consumer universe with the accepted feed scope; saved operator configuration must not be silently rewritten and REST/other-provider expansion must not be substituted. This source-path inference was not executed against the user database.

**DP-03 — output checks do not directly recheck current stream readiness (candidate safety defect requiring reproduction, high).** `_require_current_scan_data` at `scanner_engine.py:230` calls `_freshness_status`, which revalidates cached candle evidence at `:192` but does not inspect `adapter.live_feed.status()`. It is used before signal writes and finalization at `:989` and `:1045`; the deferred preview path at `:1159` similarly uses cached freshness. In contrast, `get_broker_status` at `:428` explicitly blocks when an attached stream loses readiness. If disconnect or quality degradation occurs after acquisition while the frozen last-completed candle remains fresh, the output-path checks appear capable of proceeding despite the unavailable stream. This is a source-audit candidate, not a reproduced runtime failure. Existing tests at `test_phase3_angel_integration.py:131` and `test_phase4_e2e.py:327` check health after failure, rather than this mid-scan transition. A deterministic transition test must establish the actual outcome before a minimal repair is designed. Production edits are forbidden by the current Phase 3 hard gate.

**DP-04 — Supertrend warm-up exceeds the stream cache (proven static software incompatibility, high).** `angel_feed.py:261` and `:358` cap retained 5m bars at 150. `strategies.py:1608` requires at least 200 completed bars for `evaluate_supertrend_pullback`, otherwise returning no candidate. As written, this feed cache cannot supply that evaluator's minimum, regardless of further uninterrupted tick volume. This is an implementation-capacity dependency, not merely missing external observations. Do not lower the evaluator's existing requirement or seed it with unqualified REST/history/fixtures to obtain acceptance. Cache/history retention and provenance policy require a later authorized correction and regression test.

**DP-05 — a short ingestion observation does not supply strategy warm-up or explain its absence (static contract limitation, medium).** Order Block and ORB require 30 completed bars (`strategies.py:925`, `:1441`), VWAP requires 35 (`:1121`), and Supertrend requires 200 (`:1608`). A newly connected seven-minute stream cannot provide those 5m histories. `scanner_engine.py:1130` reports `NO_ELIGIBLE_SETUP_FOR_ACCEPTED_INPUT` when no candidate exists; evaluator `None` does not separately identify warm-up shortage. Future Phase 4 explanations must distinguish insufficient inputs from a mature strategy with no setup, while preserving the rules. A legitimate `COMPLETED_EMPTY` input-consumption receipt must not be presented as strategy signal acceptance.

**DP-06 — raw-event links are retained metadata, not an enforced cross-table proof (auditability scope, medium).** `candle_lineage.py:27` preserves feed references, but `:166` validates canonical rows/local hashes and inserts cash facts without joining `angel_feed_events`. The integration fixture at `test_phase3_angel_integration.py:216` deliberately uses `offline_event`/`offline_baseline` strings and asserts batch authenticity remains `NOT_ESTABLISHED`. This is not evidence of independently authenticated market input. Real acceptance must validate the referenced raw packet hashes and cumulative-volume baseline through the actual feed store, plus candle-to-batch-to-run/signal links. If strict automatic reference enforcement is required, its store-boundary behavior must be designed and tested later rather than inferred from the presence of string IDs.
