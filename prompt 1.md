## 10. WORKSTREAM WS-SECURITY — INDUSTRY-GRADE ASSESSMENT AND REPAIR

Audit to actual deployment threat model: single-user loopback alpha versus later remotely accessible/multiuser SaaS, and make features fail closed when the latter's auth/tenant controls do not exist. The current loopback-only server is **NOT** proof that making it publicly addressable is safe.

Use OWASP ASVS 5.0.0 as checkable risk-based requirements and NIST SSDF SP 800-218 as software life-cycle baseline. In `docs/project/SECURITY_REVIEW.md`, maintain **Threat → endpoint/path → current mitigation → failing test → patch → verification → residual risk**. Cover:

- **Authorization and exposure:** enforce loopback host binding, strict origin/host checking against DNS rebinding, no CORS wildcards, safe HTTP method discipline, no remote privileged admin/scan routes. Before any remote launch, real authentication/session/authz, tenant isolation, CSRF, rate limits, abuse controls, credential lifecycle, secrets manager and security review are gating requirements. No fake login layer.
- **Input/output:** path traversal, SQL injection using parameterized queries, malicious context import or CSV, XSS/HTML escaping in opportunity explanations and user-facing strings, content-type/bounds/body-size validation, CSV formula injection on exports, deserialization risk, file import allowlist and safe filenames, request smuggling/host header misuse relevant to actual stack.
- **Secrets/privacy:** `.env` not web served, error messages sanitized, logs redacted, no API keys/tokens/customer account IDs in screenshots/docs/release; dependency/license review, secret-scanning against safe metadata; no risky uploads to external scanners without approval.
- **Transaction & money:** monotonic and immutable accounting evidence, SQLite WAL/concurrency, rollback on failure, nonpositive price or misordered target, cross-account record isolation, duplicate entries on retry, DB integrity check in throwaway copy, atomic backup/restore verified without mutating real operational DB.
- **Protocol/browser:** CSP and other relevant security headers compatible with actual app, caching policy for sensitive APIs, no third-party tracking, secure cookies if ever added, guard against GET side effects, safe local offline demo switch, strict mode boundaries.
- **Dependencies & supply chain:** Python and JS lock/pins where feasible, license notices, vulnerability inventory with offline evidence/online lookup only when explicitly approved and authorized, minimal privileges, no untrusted automatic upgrade. Generate machine-readable SBOM where tooling supports it; otherwise include deterministic dependency manifest. Build provenance under reproducible recorded commands.
- **Logging/incident:** stable request/correlation IDs without secrets, useful errors, rotation/retention policy, no credential dumps, alerting recommendations, incident playbook, backup and restore, integrity checks.

Adversarial tests must include bad origins, weird hosts, huge payloads, invalid JSON, embedded scripts in symbol/strategy explanations, malicious CSV formulas, secret paths, malformed ledger record IDs, concurrent inserts/rollbacks, API event leakage, clock skew, forged demo-mode flags, and failed optional provider. Record actual results; not all tests must be passing to ship an internal RC, but every P0/P1 security gap must be fixed or RC withheld.

**No new external-facing server deployment or user registration yet**. Prepare secure deployment architecture and environment config examples WITHOUT real values. The owner explicitly defers subscription webhooks; do not include insecure `/webhook` placeholders in production.
